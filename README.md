# Match Three

Match-3 на Unity (WebGL). Тестовое задание Playrix на позицию Software Engineer.

Выполнил Егор Фетисов, совместно с Claude Code.

**Играть:** [Cloudflare Page](https://playrix-match3-test.skrininshot-trk.workers.dev/)

**Управление:** перетащить фишку на соседнюю, тапнуть по бустеру.

---

## Что реализовано

Сделаны все три варианта Задания 2:

**Задание 1 - ядро.** Поле, матчи, каскады, опадение, автоматчи при опадении. Стартовая расстановка случайная и гарантированно без матчей. Опадение не начинается до конца эффекта удаления. Размер поля, палитра и цели уровня живут в JSON.

**2.1 - уровни.** 12 уровней, лимит ходов, победа и поражение, карта уровня с фишками заданного и случайного цвета, дозагрузка уровней и подмена уровня без перезапуска игры.

**2.2 - бустеры.** Линия, бомба, радужный шар, самолётик. Все 10 парных комбинаций. Цепочки, когда один бустер активирует другой.

**2.3 - элементы.** Ящики - обычный, цветной, меняющий цвет каждый ход, блокер. Свойства задаются данными и комбинируются между собой (несколько жизней, вложенное содержимое, размер больше одной клетки и т.д.).

## Архитектура

Проект разбит на assembly, ссылки идут строго в одну сторону:

```
Core  <-  Data  <-  Presentation  <-  App
```

Ключевое решение здесь одно: `Project.Core` не ссылается ни на что, и полностью оторван от UnityEngine. Правила, матчи, гравитация, бустеры, ящики и уровни - это чистый C#. Так что логику можно прогонять без сцены и без рендера, поэтому она покрыта быстрыми тестами, а любая партия воспроизводится по сиду.

- **`Core`** - модель доски и правила. Точка входа - фасад `Match3Game`.
- **`Data`** - загрузка уровней, сохранение прогресса.
- **`Presentation`** - отрисовка, анимации, ввод. Знает про `Core`, но не наоборот.
- **`App`** - bootstrap, UI, экран карты, склейка.

### Как устроен ход

Ход - это данные, а не корутина. `TurnResolver` целиком прокручивает последствия хода в памяти и возвращает `TurnResult`: упорядоченный список фаз, где каждая фаза содержит события - что исчезло, что переместилось, что появилось, что получило урон. `BoardView` потом просто проигрывает эти фазы одну за другой.

Опадение не может начаться раньше конца удаления, потому что это разные фазы. А каскады и цепочки бустеров разрешаются волнами внутри одной модели, без вложенных корутин - заодно это защищает от бесконечной цепочки, когда два бустера поджигают друг друга.

Побочный, но самый полезный эффект: логику можно тестировать, проигрывая тысячи ходов без единого отрисованного кадра.

### Расширяемость

**Новый бустер** - реализовать `IBoosterEffect` и зарегистрировать; комбинации с существующими типами добавляются в `BoosterCombinationRegistry` как записи, резолвер при этом не меняется.

**Новый тип ящика** - правило урона через `IObstacleDamageRule` плюс запись в `ObstacleCatalog`. Свойства ортогональны типу, поэтому «цветной ящик с тремя жизнями размером 2×2, внутри которого блокер» - это конфигурация, а не отдельный класс. Тест `AllCatalogEntriesShareOneImplementation` следит, чтобы так и оставалось.

### Формат уровня

`Assets/_Project/Resources/Levels/level_XX.json`:

```json
{
  "id": "level_01",
  "width": 7, "height": 7,
  "moveLimit": 16,
  "seed": 0,
  "palette": ["r", "g", "b", "y"],
  "goals": [{ "color": "r", "count": 28 }]
}
```

`seed: 0` - доска новая при каждой попытке. Ненулевой сид фиксирует расстановку, и уровень становится воспроизводимым: удобно и для дизайна, и для отладки бага по конкретной доске.

Необязательное поле `layout` задаёт карту построчно, один символ - одна клетка:

```
"##.....##"    #              клетка вне поля
"...R.B..."    .              случайная фишка из палитры
"..X...X.."    r g b y p o    фишка этого цвета
"...=.=..."    R G B Y P O    цветной ящик, ломается матчем этого цвета
"........."    =              обычный ящик
"...=.=..."    *              ящик, меняющий цвет каждый ход
"..X...X.."    X              блокер
```

Регистр значимый: строчная буква - фишка, заглавная - ящик под этот цвет. Всё, что богаче (лишние жизни, размер больше клетки, вложенное содержимое), задаётся через `CellOverride`, чтобы алфавит не разрастался. Полный список - `Core/Level/LayoutCodes.cs`.

## Процесс и валидация

Проект написан вместе с Claude Code - ТЗ это допускает, но мне кажется правильным описать процесс открыто.

Моя часть работы: разобрать ТЗ в спецификацию (`GAME_SPEC.md`) с явной расстановкой приоритетов - приоритет на полностью работающее ядро; выбрать стек и формат данных уровня; вести работу итерациями, принимая или отклоняя результат каждой. Так же занимался тем, что плохо делегируется: подбирал цветовую схему, шрифты и внешний вид элементов, доводил взаимодействие с бустерами ближе к референсу Homescapes, отлавливал баги, которые видны только в билде.

Проверял результат следующими способами:

**130 EditMode-тестов**: Покрыл детектор матчей, гравитацию, генерацию доски без автоматчей, резолвер хода, эффекты бустеров и их комбинации, ящики со всеми свойствами, загрузку уровней. Все тесты зелёные.

**Стресс-симуляция.**: `StressSimulationTests` вместе с `GreedyPlayer` играют случайные партии на нескольких layout'ах и проверяют инварианты доски после каждого хода. Это оказалось полезнее точечных тестов: часть багов ловится только на длинных сериях ходов, где сходятся каскад, цепочка бустеров и ящик одновременно.

**Ручное прохождение**: после каждой значимой сборки: победа, поражение по лимиту ходов, все четыре бустера и их комбинации, цепочки, уровни с ящиками, поведение при отсутствии ходов.

## Известные ограничения
- Нет пулинга view-объектов. На поле 9×9 это незаметно, на большом поле с частыми каскадами может стать заметно.
- Звук подключён как заглушка (точки вызова расставлены, но пока ассетов нет).
- Тестами покрыта логика, а не представление. Анимации, тайминги и ввод проверялись только руками и глазами.
- Пока что мобильная раскладка не проверялась. Ввод идёт через `Pointer`, поэтому касания работают, но верстку под вертикальный экран я не делал.
